WHAT EACH GATE DOES
  Worked out mechanically: find the gate branch, walk both paths a bounded
  number of instructions, and diff what they reference - string constants,
  float and integer constants, and call targets (a callee is named after the
  first distinctive string it references). Anything that survives is what the
  episode actually changes. Where nothing distinguishes the two paths the gate
  is marked UNKNOWN, with the size and shape of the code it guards so it is
  still a lead rather than a dead end.

BEFORE OPENING ANY OF THEM
  A gate is content the game runs only in one episode; opening it makes that
  content unconditional. NOT every gate should be opened. Many choose between
  two equally valid per-episode values - a constant, a model name, a sound -
  and forcing one overrides the other episode. Worked example: a patch
  labelled E2 Bullet traces was landing on a `cmp episode,1` choosing between
  the PU_SEADONE and PU_SEADONEE2 pickup names, pinning a pickup name in
  every episode for no benefit.

  Only cmp-imm gates are openable by NOPing the jump. cmp-reg and load-cmp
  need the surrounding code read first - the branch may be shared.

  Outside this file: SCM checks via GET_CURRENT_EPISODE, rpf.xml mounting and
  per-episode .dat/.img data gate a great deal that no code scan will find.
